# 第 11 轮设计案：三个新小游戏

> 状态：**设计待评审**（本文档不含任何代码改动）
> 目标：在不动主循环手感的前提下，给"敲猪 → 还债"之间插入更多有决策、有操作的玩法节点

---

## 0. 结论摘要

| 项 | 决定 |
|---|---|
| 实现方式 | **独立覆盖层模块**（同 `lucky_wheel.gd`），不碰 `challenge3d.gd` 的 3D 渲染管线 |
| 触发方式 | **天数里程碑**（第 2 / 4 / 6 天各一次，按顺序轮换三个小游戏） |
| 调度 | 新增 `event_hub.gd` 统一发牌，`main.gd` 只跟 hub 对话（只加 6 处接线） |
| 每局上限 | 3 次；与账单考核互斥（账考优先，被打断则顺延到次日） |
| 新增代码 | 约 1050 行（三个小游戏 ~900 + 调度器 ~150），`main.gd` 约 +50 行 |
| 随机性 | **零随机触发**。发牌时机只由 `game_day` 决定，测试可完全复现 |

## 1. 现状盘点

| 玩法 | 触发条件 | 实现位置 | 交互类型 |
|---|---|---|---|
| 主循环敲猪 | 常驻 | `main.gd` | 动作 |
| 金币雨（凑钱） | 账单到期（<¥300），每局≤3 | `challenge3d.gd` + `update_collect` | 空间点选 |
| 躲催债 | 账单到期（≥¥300），每局≤3 | `challenge3d.gd` + `update_dodge` | 走位躲闪 |
| 幸运转盘 | 余额过 ¥500 / 连击 12 | `lucky_wheel.gd` | 抽奖 |
| 抛硬币 | 攒够阈值 | `main.gd` 内嵌 | 微互动 |
| 选卡 3 选 1 | 每攒 ¥135 | `card_build.gd` | 构筑决策 |

**诊断**：玩法不算少，但 **80% 的事件都挤在"账单到期"这一刻**。一局 7 天里，前 3 天基本是纯敲猪，中段突然被账考连打，后段直接结算。节奏是"空 → 挤 → 结束"。

**本轮目标**：把事件摊到日历上，让每天有"下一个节点在哪"的预期感。

## 2. 共同架构

### 2.1 覆盖层模块契约

每个小游戏是一个自包含脚本（`RefCounted` 或 `Node`），只依赖 `main` 的公开状态：

```gdscript
setup(host) -> void              # 注入 main 引用，只调一次
reset_run() -> void              # 新局清状态
is_open() -> bool                # main 用它暂停整局
open_event(payload: Dictionary) -> bool   # 由 event_hub 调用；返回是否成功开启
tick(delta: float) -> void       # 只有 is_open() 时才被调
handle_click(point: Vector2) -> bool      # true = 已消费，不再往下传
handle_key(keycode: int) -> bool          # 键盘操作（电话连打需要）
draw(canvas: CanvasItem) -> void          # 自己画面板，不复用 main 的 draw_*
confirm() -> void                # 结算并关闭
```

> 为什么不像 `challenge3d` 那样做成 `phase` 分支？因为那要改 `_process` / `_unhandled_input` / `_draw` 三处主循环，每加一个模式就多一层 `if`。覆盖层模式下 `main` 只知道"有没有弹窗"，不知道弹窗里是什么。

### 2.2 事件调度器 `event_hub.gd`

```gdscript
var schedule := {2: "pawn", 4: "dice", 6: "calls"}   # 天数 → 玩法
var pending: Array[String] = []      # 排队中的事件
var served := 0                      # 本局已发牌数（上限 3）
var last_day := 0
```

职责：

1. `tick()` 里比对 `main.game_day`，跨过里程碑就入队
2. 每帧最多放行 **1 个**事件；有事件在场时其他一律排队（防同帧双弹窗）
3. 账单考核在场时**不发牌**，事件留在队列里等（顺延，不丢弃）
4. 转盘打开时不发牌（玩家主动触发优先）

`main.gd` 需要的接线只有 6 处：

| # | 位置 | 改动 |
|---|---|---|
| 1 | 常量区 | `const EventHubScript := preload("res://scripts/event_hub.gd")` |
| 2 | `_ready` | `hub = EventHubScript.new(); hub.setup(self)` |
| 3 | `reset_game` 结尾 | `hub.reset_run()` |
| 4 | `_process` | 弹窗时整局暂停：`if hub.any_open(): return`；否则 `hub.tick(delta)` |
| 5 | `_unhandled_input` | 顶部转发 `hub.handle_click / handle_key`，返回 true 就 `return` |
| 6 | `_draw` 尾部 | `hub.draw(self)` |

### 2.3 视觉基调

沿用转盘面板：`Rect2(290, 84, 700, 632)`，西部木质 + 暖黄描边，底部一颗 190×50 的确认按钮（`CONFIRM_RECT`）。三个小游戏共用同一套面板骨架和标题栏，只在中间区域换内容 —— 玩家一眼能认出"又是一个事件"，但不会以为在玩另一个游戏。

## 3. 小游戏 A：当铺砍价（`pawn_shop.gd`）

**主题**：把这一局"打到的猪"拿去当铺换现钱还债。老板是个精明的老狐狸。

### 规则

1. 弹出典当品（随机从本局砸到过的猪型里挑，如"花猪 ×6 只"），标注**基准价**
2. 下方是一条横向价格条，区间 `0.7x ~ 2.2x`，指针按正弦来回摆动
3. 玩家点击 → 指针停下，落在哪档就拿哪档的钱
4. **有 2 次机会**：第一次点完先给预览（"当前 1.35x，还点吗？"），第二次点击锁定
5. 锁定后立即入账，`score += 金额`，走正常还账流程

### 数值

| 项 | 值 | 说明 |
|---|---|---|
| 基准价 | ¥180 | ≈ 5 只普通猪，约等于 1/5 局目标 |
| 区间 | 0.7x ~ 2.2x | 实得 ¥126 ~ ¥396 |
| 分档 | 0.7~1.0 灰 / 1.0~1.6 黄 / 1.6~2.2 红 | 红色档额外播放金币爆闪 |
| 摆动周期 | 1.4s → 1.15s（第二次机会加速 20%） | 第一次好停，第二次要胆量 |

**为什么给两次机会**：只给一次是纯运气，给三次就变成刷钱。两次 = "第一次试水，第二次要不要贪" —— 这才是决策。

### 失败兜底

最差档也拿 ¥126，不会亏钱、不会倒扣。小游戏是要**奖励玩家的时间**，不是惩罚。

## 4. 小游戏 B：赌桌比大小（`dice_table.gd`）

**主题**：黑猪坐庄。它笑着推牌过来："押多少，朋友？"

### 规则

1. 发牌：庄家明一张暗一张，玩家两张明牌
2. 玩家选押注额：`¥50 / ¥120 / 全部身家的 30%`（三选一，按钮式）
3. 然后 `要牌` 或 `停牌`，最多加到 5 张
4. 点数 >21 爆牌，立刻输；否则与庄家比大小，**庄家 17 点以下必须继续要牌**（标准 21 点简化规则）
5. 赢 → 押注额入账；平 → 退回押注；输 → 扣掉押注

### 数值与保护

| 项 | 值 |
|---|---|
| 押注档位 | ¥50 / ¥120 / `min(余额×0.3, 最便宜账单金额)` |
| 上限硬约束 | 单次押注 ≤ 余额 35% —— **不许一把梭哈直接破产** |
| 庄家 AI | 17 点停牌（含软 17 停），标准且可预期 |
| 结算 | 赢取押注额等值现金，不翻倍（翻倍会让经济崩） |

**破产保护**：如果余额 < ¥50，这个事件自动换成「赊账局」—— 免费玩，赢了给 ¥80，输了只掉体力。保证低分玩家也能体验，而不是被跳过。

## 5. 小游戏 C：催债电话连打（`collection_calls.gd`）

**主题**：八个催收员同时打你电话。你得按"响铃顺序"一个个挂掉。

### 规则

1. 屏幕上散落 4~6 个来电气泡（编号 1-6，错位摆放）
2. **记忆阶段**（1.5s）：依次高亮，玩家看顺序
3. **复现阶段**（6s）：按顺序点击 / 按数字键
4. 全对 → 成功；错一次 → 立即失败（不重置，直接判负）

### 难度曲线

| 第几次触发 | 气泡数 | 记忆时长 | 复现时限 |
|---|---|---|---|
| 第 1 次（day 2） | 4 | 1.5s | 6.0s |
| 第 2 次（day 4） | 5 | 1.3s | 5.5s |
| 第 3 次（day 6） | 6 | 1.1s | 5.0s |

### 奖惩

| 结果 | 效果 |
|---|---|
| 成功 | `score += ¥120`，并**清掉该账单的催收进度**（如果它带 collection 效果） |
| 失败 | 扣体力 45，+1 层催收进度（不罚款、不滞纳） |

**为什么和金币雨不重复**：金币雨考"空间判断 + 手速"，电话连打考"顺序记忆"。一个用锤子/光标，一个用数字键和点击，肌肉记忆完全不冲突。

## 6. 节奏与冲突（关键风险）

一局的日历（按 `¥135/天`、目标 `¥950` 估算）：

```
day 1 ───── day 2 ───── day 3 ───── day 4 ───── day 5 ───── day 6 ───── day 7
  纯敲猪    当铺砍价    (选卡)     赌桌比大小   (账考可能)  电话连打    结算
             ↑经济决策             ↑赌博胆量                ↑记忆操作
```

**冲突规则（按优先级从高到低）**：

1. **幸运转盘**：玩家主动触发，永远最高优先，转盘开着就不发牌
2. **账单考核**：涉及逾期惩罚，不能被打断；小游戏顺延到次日
3. **小游戏**：排队，一次只放一个，间隔 ≥0.5s
4. 已结算 / 破产 / 结算界面：不发牌

**跨多天时的处理**：`advance_calendar` 的 `while` 循环可能一帧跨 2 天（收入跳变），调度器用 `last_day` 记录已处理到哪天，跨过的里程碑全部入队，但**仍然一次只放一个**。

## 8. 测试计划（预计 +28 条断言）

| 断言组 | 内容 |
|---|---|
| 调度 | day2 只发一次；一帧跨 2 天时两个事件都入队但只开一个；账考在场时顺延；`max_per_run` 生效；`reset_run` 清空 |
| 当铺 | 点击落在各档的金额正确；两次机会的第二次锁定；最小档不倒扣；结算后 `score` 增量正确且触发还账 |
| 赌桌 | 押注上限被夹紧（余额 35%）；爆牌即输；庄家 17 停牌；平局退回；低余额走赊账局 |
| 电话 | 全对成功加分；错一次即失败扣体力；第 3 次难度参数生效 |
| 隔离 | 三个弹窗任一打开时 `phase` 冻结、猪不移动、卡不计时、转盘不刷新 |

外加**连跑 4 次**验证零随机（本轮设计的核心卖点：零随机触发，所以理论上应该永远全绿）。

## 10. 需要你拍板

1. **难度定位**：现在账考是"失败要命"（逾期+滞纳+罚款）。三个新小游戏我设定的是"最差也不亏本金"（当铺保底 0.7x，赌桌有押注上限，电话输了只掉体力）—— 你希望它们**更硬核**（输了真扣钱）还是保持现在的**宽松奖励型**？
2. **赌桌尺度**：21 点规则要不要再简化（比如只比大小、不要牌）？简化后代码少 80 行，但决策深度会掉。
3. **当铺次数**：现在设计是 2 次点击。要不要改成"每局内的当铺次数越多，老板压价越狠"（第 2 次 0.9x、第 3 次 0.8x），逼玩家省着用？
4. **是否要第 4 个**：还有一个我想到但没写进来的 —— **"猪圈夜班"（30 秒限时闪电战，猪变快、收益翻倍、但账单倒计时也加速）**。要不要一起做？
